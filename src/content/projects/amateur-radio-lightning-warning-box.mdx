I started this because I wanted a small lightning warning box I could use around radio operations without depending on a phone, a browser or an internet connection to tell me that nearby electrical activity might be worth paying attention to.

The sensor is an AS3935, with a XIAO ESP32-C6 doing the rest of the work. The AS3935 can distinguish between `NOISE`, `DISTURBER` and `LIGHTNING` events and, for lightning events, provide an estimated storm distance and an energy value. The ESP32-C6 gives me enough room around that to add a proper local interface, physical controls, persistent logging and eventually network access without turning the basic detector into a much larger computer than it needs to be.

The important bit, though, was the order I built it in. I did not want Wi-Fi, web pages and logging sitting on top of a sensor path I had never properly proved. So the project has grown in three stages: get the AS3935 working reliably first, turn that into something I could actually operate second, and only then start adding connected features.

## First, make the sensor behave

M1 was deliberately boring. The job was to get SPI communication, the AS3935 interrupt line and event decoding working repeatedly on the actual XIAO ESP32-C6 hardware.

That also meant dealing with calibration properly rather than relying on whatever happened to work in the first sketch. The MOD-1016 module I am using came with a factory `TUNE_CAP` value, so the firmware applies that explicitly and then runs oscillator calibration at startup. The current module value is `7`, which corresponds to 56 pF.

The other early lesson was that the bench itself is a fairly hostile place to test a lightning detector.

USB supplies, computers, displays and assorted electronics generate plenty of electrical rubbish, and the sensitive settings that are useful when looking for weak events can produce a stream of `NOISE` interrupts in that environment. Rather than continually editing constants while testing, I added two sensor profiles.

`SENSITIVE` uses the AS3935 indoor AFE with a lower noise floor and permissive watchdog and spike-rejection settings. `NOISY` uses the outdoor AFE, maximum noise floor and much stricter filtering. MUTE held on during boot originally became the quick way of selecting the latter.

That proved useful enough that the profile system survived into the later firmware rather than being thrown away as a bench hack.

M1 also established a simple fault-code scheme. If sensor initialisation, configuration or interrupt attachment fails, the firmware stops and reports a `0x1XX` code instead of carrying on in a half-working state and making me debug whatever nonsense happens afterwards.

By the end of M1, `NOISE`, `DISTURBER` and `LIGHTNING` events were being decoded reliably and the basic alert path was working.

## Turning it into an actual warning box

M2 was where the breadboard stopped being just a sensor test.

I added the OLED, ARM and MUTE switches, RESET/ACK button, proper input debounce, an event buffer and the buzzer path. That sounds like a pile of small additions, but together they changed the way the device could be used. I no longer needed a serial terminal open to know what the sensor thought was happening.

The OLED shows the active profile, ARM and MUTE state, event counters and recent events. Lightning detections retain the distance and energy values from the AS3935, while the small ring buffer lets the display roll through recent activity instead of showing only whatever happened last.

The physical controls are deliberately simple. ARM decides whether AS3935 events are being acted on, MUTE suppresses the audible warning, and RESET/ACK clears the current counters and latched lightning state. All three use active-low inputs with the ESP32 pull-ups enabled, and M2 added debounce because switches are mechanical devices and therefore quite capable of lying several times in a few milliseconds.

The buzzer managed to consume more bench time than its complexity really justified.

The passive piezo is driven through a PN2222A transistor from `D6`, and the final bench arrangement includes a 4.7 kOhm collector pull-up to +5 V. Without that, the alert path was inconsistent enough to make firmware debugging misleading. Once the transistor stage was wired properly, the same firmware that had appeared suspicious suddenly became rather less mysterious.

That is why there is still a separate `buzzer_test.ino` in the project. If the buzzer stops working, I would much rather test three components and a transistor in isolation than immediately start excavating the lightning-detection code.

## Adding networking without breaking the useful bit

M3 started shortly afterwards, at about 00:44 AEST on 8 March.

The main rule for this stage is that none of the connected features gets to become a dependency of the local warning system. A lightning detector that stops being useful because the access point has disappeared would be an impressively stupid improvement over M2.

So Wi-Fi, NTP, persistent logging and HTTP access sit around the existing local behaviour rather than replacing it.

The final M3 firmware connects as a Wi-Fi station when credentials are configured, attempts an NTP time sync, and keeps retrying if either the network or clock is unavailable. If Wi-Fi is not configured or cannot connect, the box can still continue locally.

Lightning strikes are stored in an NVS-backed ring buffer so the recent history survives a restart. Each record can contain the timestamp, estimated distance and energy reported for the event. When the network is available, that information is exposed through a very small HTTP interface:

- `/` for a basic status page
- `/api/status` for the current device state
- `/api/strikes` for stored strike history

The credentials in the public firmware are deliberately placeholders.

M3 has also accumulated a few changes that came directly out of bench use. Startup now has a stabilisation period before AS3935 event logging is enabled, which stops the detector treating its own startup activity as something meteorological. Profile changes briefly quiet the event path for the same reason.

The RESET button now does two jobs without adding another control to the box. A normal press still acknowledges the state and clears the counters, while a long press switches between `SENSITIVE` and `NOISY`. There is also a short boot-time assist window so moving MUTE on just after power-up can still select the noisy profile rather than requiring perfectly choreographed switch timing.

The OLED has become useful during startup too. Instead of sitting blank while the firmware initialises everything, it shows the boot process, including the firmware revision, stored-log state, OLED detection, selected profile, Wi-Fi state and startup guard. This was mainly added because watching a little black rectangle and wondering whether it had crashed was getting old.

Once startup is finished, it returns to the normal live event display.

## Core hardware

Start with the XIAO ESP32-C6 and AS3935 only. Use SPI for the sensor and connect its IRQ line to `D2`.

Once that works, add the OLED on I2C using `D4` for SDA and `D5` for SCL. Then add the ARM and MUTE switches and RESET/ACK button as active-low inputs using the internal pull-ups.

Add the buzzer stage last. In the current build, `D6` drives a PN2222A through a 1 kOhm base resistor, with the passive piezo on the transistor stage and a 4.7 kOhm pull-up from +5 V to the collector.

Before applying power, make sure every section shares a common ground and check the PN2222A pinout against the actual transistor you have. Transistor pinouts are sufficiently inconsistent between packages and manufacturers that assuming yours matches the diagram is an excellent way to waste an evening.

Expected result:

- stable 3.3 V and 5 V rails
- no components getting warm
- no floating control inputs
- AS3935 correctly strapped for SPI operation

If any of those are wrong, fix the hardware before introducing firmware as another variable.

## Continuity and bring-up

Check for a hard short between `3V3` and ground. Then verify the paths that matter for initial bring-up:

- AS3935 IRQ to `D2`
- AS3935 SPI lines to `D8`, `D9` and `D10`
- chip select to `D3`
- buzzer drive from `D6` through the transistor stage
- common ground across the complete breadboard

If one of those paths is wrong, stop there. Firmware cannot repair copper.

## Proving M1

Flash `firmware/m1_bringup/m1_bringup.ino` and open the serial monitor at `115200`.

The startup output should identify the board and active sensor profile, apply the AS3935 tune capacitance, calibrate the oscillator and then report that it is waiting for events.

For bench testing I used a combination of piezo clicks and nearby electrical interference to exercise the sensor. The important result is not that every improvised trigger gets labelled `LIGHTNING`; it is that the interrupt path works and the firmware is correctly reporting the AS3935 classifications as `NOISE`, `DISTURBER` or `LIGHTNING`.

If the bench produces an endless stream of noise events, start with the `NOISY` profile rather than immediately assuming the detector is broken. MUTE on during boot selects `NOISY` in the current firmware.

If M1 does not start:

- check the correct XIAO ESP32-C6 board target and upload port
- confirm the module tune-cap value and oscillator calibration
- check `SI` and the SPI wiring
- use the `0x1XX` fault code to identify which part of AS3935 startup failed

## Proving M2

Flash `firmware/m2_core/m2_core.ino`. M2 should retain the working sensor behaviour from M1 and add the operator interface.

Check each physical control individually:

- **ARM:** state changes once per operation, OLED and serial output agree, and event handling is active only when armed
- **MUTE:** state changes cleanly, warnings are suppressed, and sensor events continue to be counted
- **RESET/ACK:** the press is debounced, counters and latched state clear, and the acknowledgement chirp occurs when not muted

The OLED should respond at `0x3C` or `0x3D`, show the current profile and control states, then update its counters and recent-event line as activity occurs.

If the display behaves strangely, check for an actual I2C ACK rather than trusting an apparently successful library initialisation call. If the buzzer does not work, flash `firmware/buzzer_test/buzzer_test.ino` and prove the buzzer/transistor circuit independently before changing the detector firmware.

## Testing M3

Flash `firmware/m3_connected/m3_connected.ino` and set local Wi-Fi credentials before testing the connected functions. The credentials shown in the public source are placeholders.

During startup, check:

- OLED initialisation and stored strike-log load
- selected sensor profile
- Wi-Fi connection and assigned IP address
- NTP time synchronisation
- startup guard completion and AS3935 events becoming enabled afterwards

Then trigger test events and check the local interface again before worrying about the network. M3 is supposed to extend M2, not quietly break it.

Once local behaviour is confirmed, test `http://DEVICE-IP/`, `http://DEVICE-IP/api/status` and `http://DEVICE-IP/api/strikes`. Trigger and store several lightning events, restart the board and confirm that the NVS ring buffer survives the power cycle.

If the network side fails, separate the problem into Wi-Fi association, NTP and HTTP rather than debugging all three at once. Likewise, test persistence independently of the web API.

### Wiring matrix

| Signal | XIAO ESP32-C6 | Direction | Current wiring |
| --- | --- | --- | --- |
| ARM switch | `D0` | Input | `INPUT_PULLUP`, active low |
| MUTE switch | `D1` | Input | `INPUT_PULLUP`, active low |
| AS3935 IRQ | `D2` | Input | External interrupt |
| AS3935 CS | `D3` | Output | SPI chip select |
| OLED SDA | `D4` | I/O | I2C SDA |
| OLED SCL | `D5` | Output | I2C SCL |
| Buzzer drive | `D6` | Output | 1 kOhm into PN2222A base |
| RESET / ACK | `D7` | Input | `INPUT_PULLUP`, active low |
| SPI SCK | `D8` | Output | AS3935 SPI |
| SPI MISO | `D9` | Input | AS3935 SPI |
| SPI MOSI | `D10` | Output | AS3935 SPI |

### Current sensor profiles

The current MOD-1016 tune-cap setting is `bits = 7`, or `7 × 8 pF = 56 pF`.

| Profile | AFE | Noise floor | Watchdog | Spike rejection | Minimum lightning |
| --- | --- | ---: | ---: | ---: | ---: |
| `SENSITIVE` | Indoor | 2 | 1 | 1 | 1 |
| `NOISY` | Outdoor | 7 | 6 | 6 | 1 |

`SENSITIVE` is the normal starting point. `NOISY` is there for electrically ugly environments, particularly the bench where half the equipment around the detector seems determined to participate in the experiment.

## Troubleshooting

  <details><summary>It will not compile or upload</summary><p>Use the explicit XIAO ESP32-C6 board target. Do not use a generic ESP32 family profile if it produces partition or upload problems. Also check the selected serial port before spending time inspecting code that never reached the board.</p></details>
  <details><summary>The AS3935 reports noise constantly</summary><p>Try the <code>NOISY</code> profile. Also confirm that the module tune-cap value is being applied and oscillator calibration succeeds at startup. A busy electronics bench is a poor imitation of a quiet outdoor RF environment, so some adjustment is expected.</p></details>
  <details><summary>The OLED is blank</summary><p>Check for I2C acknowledgement at <code>0x3C</code> and <code>0x3D</code>. Do not rely only on the display library returning success. The current firmware checks that a device actually answers on the bus and can continue headless if the OLED is absent.</p></details>
  <details><summary>The buzzer is silent</summary><p>Check the PN2222A orientation, 1 kOhm base-resistor path, passive-piezo wiring, common ground and the <code>+5V → 4.7 kOhm → collector</code> pull-up. ## Where this led

The standalone warning box proved the part I most needed to understand: the local sensor path could classify events, present useful state and raise an alarm without depending on anything beyond the device itself.

The work that once sat on this page as a list of things still to do—network testing, safer deployment configuration, persistent reporting and field-ready packaging—eventually pointed beyond a single enclosed detector. Those concerns now live in BrambleNet, where the lightning sensor becomes one self-reporting node among a broader home and field network.

This prototype therefore stays as a record of the decisions that got me there. It captures the original AS3935 and ESP32-C6 hardware, the deliberately staged firmware work, and the point where a useful standalone warning box began turning into a rather larger idea.
